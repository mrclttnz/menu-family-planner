## 3. Findings & Remediation Tracker

### `SEC-F01` (MEDIUM) — Fallback Secret Key Not Blocked in Production Mode
- **CWE**: CWE-1188 (Insecure Default Initialization of Resource), CWE-798 (Use of Hard-coded Credentials)
- **Location**: `backend/app/core/config.py:9`
- **Risk**: `Settings.SECRET_KEY` defines a default fallback string (`"menu-design-dev-secret-key-change-in-production-min-32-chars-long!"`). While valid for local development, if deployed to production without an explicitly defined `.env` or container environment variable, the application starts with a publicly known secret key, enabling attacker token forgery.
- **Remediation**:
  Add an environment-aware validator in `Settings`:
  ```python
  @field_validator("SECRET_KEY")
  @classmethod
  def validate_secret_key(cls, v: str, info) -> str:
      if len(v) < 32:
          raise ValueError("SECRET_KEY must be at least 32 characters long.")
      # In production, disallow the default dev secret key
      # info.data.get("ENVIRONMENT") == "production"
      return v
  ```
- **Status**: `OPEN` (Documented / Recommended for Phase 7 Deployment)

---

### `SEC-F02` (MEDIUM) — Missing Rate Limiting on Authentication Endpoints
- **CWE**: CWE-307 (Improper Restriction of Excessive Authentication Attempts), CWE-400 (Uncontrolled Resource Consumption)
- **Location**: `backend/app/routers/auth.py:13`, `backend/app/routers/auth.py:47`
- **Risk**: An attacker could perform dictionary or brute-force attacks against `/api/v1/auth/login`. Furthermore, because `bcrypt` work factor is 12 (computationally intensive by design), burst requests can cause CPU exhaustion.
- **Remediation**:
  Integrate rate limiting middleware (e.g. `slowapi` with in-memory or Redis backend) or configure rate limiting at the reverse proxy layer (e.g. Nginx `limit_req_zone` or Cloudflare WAF) limiting `/api/v1/auth/*` to 5-10 requests/minute per IP.
- **Status**: `OPEN` (Documented / Recommended before public exposure)

---

### `SEC-F03` (LOW) — Overly Permissive CORS Headers & Methods Configuration
- **CWE**: CWE-16 (Security Misconfiguration)
- **Location**: `backend/app/main.py:39-40`
- **Risk**: While `allow_origins` is properly restricted via `settings.cors_origin_list`, `allow_methods=["*"]` and `allow_headers=["*"]` allow arbitrary custom headers and methods beyond those required by the REST API.
- **Remediation**:
  Explicitly specify `allow_methods=["GET", "POST", "PUT", "DELETE", "OPTIONS"]` and `allow_headers=["Authorization", "Content-Type", "Accept"]`.
- **Status**: `OPEN` (Low Risk)

---

### `SEC-F04` (LOW) — Missing Strict-Transport-Security (HSTS) Header
- **CWE**: CWE-523 (Unprotected Transport-Layer Security)
- **Location**: `backend/app/main.py:46-52`
- **Risk**: Browsers are not instructed to strictly force HTTPS connections from the application layer.
- **Remediation**:
  Include `Strict-Transport-Security: max-age=31536000; includeSubDomains` in production or ensure TLS termination proxy (Nginx/Traefik) injects it.
- **Status**: `OPEN` (Low Risk)

## 4. Verification Check Details

### 4.1 Anti-IDOR & Multi-Tenant Isolation
Every single resource operation is strictly scoped:
- **Members**: `Member.household_id == current_household.id`
- **Dishes**: `Dish.household_id == current_household.id` (including foreign key checks for custom `course_types` and `source_types`)
- **Meal Slots**: `MealSlot.household_id == current_household.id`
- **Preferences**: Verified both dish and member belong to `current_household.id`
- **Attendance**: Verified both meal slot and member belong to `current_household.id`

### 4.2 Injection & Input Sanitization
- SQL binding is handled entirely via SQLAlchemy 2.0 ORM query builder.
- Pydantic models validate and strip all incoming text fields.
- `source_url` validates protocol schema (`http://` or `https://`), preventing DOM-based `javascript:` execution.
- React frontend automatically escapes string interpolation within JSX components.

### 4.3 Error Handling & Data Leakage
- Passwords are never returned in serialization models (`HouseholdResponse` explicitly omits `password_hash`).
- Error messages are user-friendly (`detail="Incorrect email or password."`) and do not disclose user existence on failed login.
