## 3. Findings & Remediation Tracker

### `SEC-F01` (MEDIUM) — Fallback Secret Key Not Blocked in Production Mode
- **CWE**: CWE-1188 (Insecure Default Initialization of Resource), CWE-798 (Use of Hard-coded Credentials)
- **Location**: `backend/app/core/config.py:9`
- **Risk**: `Settings.SECRET_KEY` defines a default fallback string (`"menu-design-dev-secret-key-change-in-production-min-32-chars-long!"`). While valid for local development, if deployed to production without an explicitly defined `.env` or container environment variable, the application starts with a publicly known secret key, enabling attacker token forgery.
- **Remediation**:
  Add an environment-aware validator in `Settings`:
  ```python
  @field_validator("SECRET_KEY")
  @classmethod
  def validate_secret_key(cls, v: str, info) -> str:
      if len(v) < 32:
          raise ValueError("SECRET_KEY must be at least 32 characters long.")
      # In production, disallow the default dev secret key
      # info.data.get("ENVIRONMENT") == "production"
      return v
  ```
- **Status**: `REMEDIATED`. `Settings` validator in `backend/app/core/config.py` enforces length >= 32 and rejects the default dev key when `ENVIRONMENT` is `production` (case-insensitive since S25; fails at startup). It does not check key strength beyond length >= 32. Regression test in `test_security_headers_cors.py`; broader config tests planned in S30 (TG-1).

### `SEC-F02` (MEDIUM) — Missing Rate Limiting on Authentication Endpoints
- **CWE**: CWE-307 (Improper Restriction of Excessive Authentication Attempts), CWE-400 (Uncontrolled Resource Consumption)
- **Location**: `backend/app/routers/auth.py:13`, `backend/app/routers/auth.py:47`
- **Risk**: An attacker could perform dictionary or brute-force attacks against `/api/v1/auth/login`. Furthermore, because `bcrypt` work factor is 12 (computationally intensive by design), burst requests can cause CPU exhaustion.
- **Remediation**:
  Integrate rate limiting middleware (e.g. `slowapi` with in-memory or Redis backend) or configure rate limiting at the reverse proxy layer (e.g. Nginx `limit_req_zone` or Cloudflare WAF) limiting `/api/v1/auth/*` to 5-10 requests/minute per IP.
- **Status**: `REMEDIATED` in S24 (#24): in-app limiter on login/register (`backend/app/core/rate_limit.py`), 429 + `Retry-After`, forwarded headers trusted only from `TRUSTED_PROXY_IPS`; tests in `backend/tests/test_rate_limit.py`. Independently audited at the S24 gate (section 6). Residual: per-process state (single worker), no per-account lockout.

### `SEC-F03` (LOW) — Overly Permissive CORS Headers & Methods Configuration
- **CWE**: CWE-16 (Security Misconfiguration)
- **Location**: `backend/app/main.py:39-40`
- **Risk**: While `allow_origins` is properly restricted via `settings.cors_origin_list`, `allow_methods=["*"]` and `allow_headers=["*"]` allow arbitrary custom headers and methods beyond those required by the REST API.
- **Remediation**:
  Explicitly specify `allow_methods=["GET", "POST", "PUT", "DELETE", "OPTIONS"]` and `allow_headers=["Authorization", "Content-Type", "Accept"]`.
- **Status**: `REMEDIATED` in S25 (#25): `allow_methods=[GET, POST, PUT, PATCH, DELETE, OPTIONS]`, `allow_headers=[Authorization, Content-Type, Accept]` (PATCH added to the suggested list because the API and SPA use it). Tests: `backend/tests/test_security_headers_cors.py`.

## 6. Slice S24 Addendum (2026-11-21): Auth Rate Limiting (#24, SEC-F02)

Scope: `git diff 234ed5b..d12a45f` (`rate_limit.py`, `config.py`, `auth.py`, compose, `.env.example`, runbook, tests). Test suite: 54 passed.

**Verdict: PASS_WITH_WARNINGS** (no CRITICAL/HIGH). Trusted-proxy logic is correct and fails closed on malformed headers/CIDRs; forwarded headers are ignored unless the direct peer is trusted; XFF is walked right-to-left; Retry-After is correct; limiter state is lock-protected; throttled attempts are not recorded (no self-extending lockout).

| # | Sev | Location | Finding | Remediation |
|---|-----|----------|---------|-------------|
| 1 | MEDIUM | `rate_limit.py` `_enforce`/`hit`, `_purge` | Unbounded key growth. Purge only removes expired keys and only above 10k keys; with >10k active keys (reachable via IPv6 address rotation in a /64, or spoofed headers if a trusted range is misconfigured) memory grows without bound and each hit runs an O(n) purge under the global lock (CPU DoS of auth). | Hard cap (evict oldest / fail closed to a shared overflow bucket); amortize purge (time-based, not per hit). |
| 2 | MEDIUM | `resolve_client_ip` | IPv6 clients are keyed per /128, so one attacker with a /64 gets effectively unlimited buckets (bypass of bcrypt-CPU protection). IPv4-mapped forms are not normalized: `::ffff:1.2.3.4` and `1.2.3.4` are different keys; a mapped peer (`::ffff:172.18.0.2`) is not matched by an IPv4 trusted CIDR (verified), so it silently degrades to one shared bucket. | Normalize via `ipv4_mapped`; key IPv6 on /64. |
| 3 | MEDIUM | runbook / `.env.example` | Advice to trust the whole docker subnet. Docker NAT/userland-proxy can make LAN clients hitting published port 8000 appear from the bridge gateway (inside that subnet); then `CF-Connecting-IP` is attacker-controlled (CF header also takes precedence over XFF) and the limit is bypassed. | Document trusting only the cloudflared container (static IP/`/32`) and not publishing 8000 on the LAN when the tunnel is used; verify with a spoofed-header test. |
| 4 | LOW | `hit()` | `AUTH_RATE_LIMIT_PER_MINUTE<=0` raises IndexError (verified) -> HTTP 500 on all auth (fail-closed but an outage, bad UX). `AUTH_RATE_LIMIT_ENABLED=false` silently disables the limiter. | Validate `>=1` in settings (Pydantic `Field(ge=1)`); log a warning when disabled. |
| 5 | LOW | design | Per-IP only; no per-account throttling, so distributed credential stuffing on one account is not slowed. Unset `TRUSTED_PROXY_IPS` behind the tunnel puts all users in one bucket (self-DoS, documented). In-memory, single worker only (documented). | Optional per-email counter; keep Cloudflare WAF rule. |
| 6 | LOW (pre-existing) | `auth.py` | Enumeration: register returns 409 for existing email; login skips bcrypt for unknown email (timing). 429 is IP-based and adds no new oracle. | Dummy-hash verify on login; consider generic register response. |

Positives: spoofed XFF/CF headers from untrusted peers ignored (verified); malformed hop or CIDR -> peer IP (fail closed); the limiter sits before the bcrypt work and counts 422/401/409 attempts alike.

**Remediation (same slice, tests 59/59):** #1 fixed (LRU hard cap, O(1) eviction, no per-hit purge); #2 fixed (IPv4-mapped normalized, IPv6 keyed per /64); #3 fixed (docs and `.env.example` now require the exact cloudflared IP as `/32`; tests for gateway peer and mapped peer); #4 fixed (`AUTH_RATE_LIMIT_PER_MINUTE >= 1` validated, warning logged when disabled). #6 login timing fixed (dummy bcrypt verification for unknown emails, test added). Register 409 enumeration and per-account throttling (#5) remain in GitHub issue #35 because they need a product decision. Gate result stays **PASS_WITH_WARNINGS**; no re-audit of the fixes by `security-engineer` yet.

**Re-verification (2026-11-21, security-engineer, Gate 6, scope `git diff d12a45f..4583119`, tests 60 passed):**
- Finding 1 (unbounded key growth): **VERIFIED FIXED.** `hit()` uses an `OrderedDict` with a hard cap of 10,000 keys and O(1) `popitem(last=False)` on insert; the per-hit O(n) purge is gone; all mutations run under the lock, so there is no race. Evicting a blocked key only resets that key's budget, which costs the attacker 10,000 distinct source keys (distinct IPv4 or /64) within the window; this is equivalent to using fresh sources and is not a new bypass. Test `test_tracked_keys_are_hard_capped` covers the cap.
- Finding 2 (IPv4-mapped / IPv6 /64): **VERIFIED FIXED.** `_valid_ip` normalizes `::ffff:a.b.c.d` to IPv4, so mapped peers match IPv4 trusted CIDRs and share a key with the plain form; `limiter_key` buckets IPv6 per /64. Normalization is applied identically to peers and header hops, and unparsable values still fail closed to the peer IP; no trust confusion or spoofing path found. Tests cover mapped peer and /64 grouping.
- Finding 3 (trusted proxy /32 guidance): **NOT FIXED (documentation only, residual).** `.env.example`, ARCHITECTURE 6.1 and the runbook prose now correctly require the cloudflared container IP as `/32`, and tests cover the gateway-peer (not trusted under `/32`) and mapped-peer cases. Required: change the placeholder to e.g. `<IP_cloudflared>/32`. No code change needed. Also note: the runbook does not state that port 8000 should be unpublished behind the tunnel (optional hardening).

**Re-verification gate result: PASS_WITH_WARNINGS** (no CRITICAL/HIGH; code fixes for findings 1 and 2 accepted; finding 3 stays open as a one-line doc fix, to be closed without a new audit by editing the runbook placeholder).
